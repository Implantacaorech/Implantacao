## Busca semântica sobre o Vault (RAG-lite, implementado em 2026-07-19)

`tools/vault_busca_semantica.py` — protótipo real e funcional, não um design especulativo:

- Embeddings via API Gemini (`gemini-embedding-001`, mesma chave já validada em
  [[22 - Troubleshooting]]), cacheados em `tools/data/vault_embeddings.json` (gerado, fora
  do git — só reprocessa notas cujo hash de conteúdo mudou).
- Busca por cosseno em memória — o Vault tem só dezenas de notas, não precisa de banco
  vetorial de verdade.
- **Testado de ponta a ponta:** 27 notas indexadas; a pergunta *"como fazer login e renovar
  o token"* trouxe [[10 - Fluxogramas]] e [[09 - Casos de Uso]] como top resultados
  (score de cosseno 0.67 e 0.64) — exatamente onde esse assunto vive.

```bash
python tools/vault_busca_semantica.py --indexar        # (re)constrói o índice
python tools/vault_busca_semantica.py "sua pergunta"    # busca
```

**Isto é deliberadamente "RAG-lite"**, não o "banco vetorial + Knowledge Graph +
indexação inteligente" completo pedido no prompt original — ver por quê e o que falta em
[[19 - Roadmap]]. Não toca em `backend`/`frontend` de produção; é uma ferramenta de
documentação, no mesmo espírito de `tools/gerar_*`.

## Telemetria real de execução de agentes (implementado em 2026-07-19)

Diferente do RAG-lite acima, isto **toca produção de propósito**: um módulo real
(`backend/src/agentes/`) que registra cada execução de agente/subagente
(`.claude/agents/`) — não é simulação nem mock, só existe linha na tabela quando um agente
de verdade chama a API.

- **Banco:** tabela `agente_execucoes` (ver [[05 - Banco de Dados]]) — `agente`,
  `agentePaiId` (hierarquia), `tarefa`, `status` (`em_execucao`/`concluido`/`falhou`),
  `iniciadoEm`/`concluidoEm`.
- **API** (`/api/agentes/*`, JWT obrigatório): `POST execucoes` (qualquer autenticado —
  o próprio agente reportando), `PATCH execucoes/:id` (conclui), `GET execucoes` e
  `GET grafo` (só `PERFIS_GESTAO` — é o dashboard).
- **Grafo estático real:** os 13 agentes de `.claude/agents/` + as relações extraídas do
  texto de cada um (`backend/src/agentes/grafo-agentes.const.ts`) — não é um layout
  inventado, é o "quem aciona quem" já documentado em cada agente.
- **Frontend:** painel "Agentes de IA" dentro do **Centro de Monitoramento Operacional**
  (`/monitoramento`) — grafo SVG (nós = agentes, aresta = relação, pulso verde = ativo
  agora) + feed de execuções recentes, atualizando por polling a cada 4s (sem WebSocket).
- **Conta de serviço:** `sistema-agentes` (perfil Consultor) — para agentes reportarem via
  API sem usar credencial de um humano real. Só tem permissão de `POST`/`PATCH`
  (`@Roles()` vazio = qualquer autenticado); não lê o dashboard (`PERFIS_GESTAO`), então
  `GET /api/agentes/grafo` com o token dela dá 403 de propósito — comportamento correto,
  não bug.
- **Prova real, não simulada:** testado via 4 specs e2e (`backend/test/agentes.e2e-spec.ts`)
  E via chamada HTTP real em produção (login como `sistema-agentes`, 4 execuções
  registradas e concluídas refletindo trabalho genuíno desta sessão — confirmado por query
  direta em `painel_novo.agente_execucoes`, não por confiança cega na API).
- **Por que polling e não WebSocket:** tela de baixo tráfego (uso interno, poucas pessoas)
  — não compensa a complexidade de um gateway WebSocket para isso agora. Fica como
  melhoria futura se o uso justificar.

**Se você é um agente/subagente executando uma tarefa real:** reporte via
`POST /api/agentes/execucoes` no início e `PATCH /api/agentes/execucoes/:id` ao concluir,
autenticado como a conta `sistema-agentes` (ou outra de sua escolha) — é assim que o grafo
em Monitoramento Operacional deixa de ficar vazio. Nunca escreva na tabela fingindo uma
execução que não aconteceu.
